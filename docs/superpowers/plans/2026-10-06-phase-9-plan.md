# Phase 9 — Web Beta / Polish Plan

**Status: planned / ready to execute. Parent: #27.**

Phase 9 turns the Content Alpha into a stable, visually legible, feature-complete web beta. It does not add a new gameplay architecture.

Canonical interface direction: `docs/INTERFACE_AND_DISTROS.md`.

## P0 — UI foundation + semantic visual language

Establish the shared presentation substrate before restyling individual apps.

Deliver:
- shadcn/ui component foundation,
- semantic design tokens,
- typography and spacing rules,
- icon/status vocabulary,
- truth-level treatments,
- Motion + CSS motion policy,
- accessibility-safe focus and non-color cues.

Constraints:
- no simulation changes,
- no hidden-state leaks,
- no app forced into one generic card/dashboard look.

Exit:
- representative shared controls and one app prove the design system,
- reduced-motion path exists,
- existing gameplay commands remain unchanged.

## P1 — OS shell + distro/theme architecture

Make the computer feel like an operating environment rather than one hard-coded dark theme.

Deliver:
- shell tokens/profile contract,
- Ghost/OS,
- Lattice,
- Velvet,
- Daybreak,
- Petal,
- theme variants where useful,
- persisted presentation selection,
- distro switching/setup UI,
- window chrome / launcher / panel integration.

Constraints:
- distros are presentation only,
- same app/component tree where practical,
- no rank/capability/economy benefit.

Exit:
- switching distros changes presentation but produces byte-identical gameplay state,
- every distro remains readable with accessibility overrides.

## P2 — Visual-first app information

Replace avoidable text/menu friction with meaningful visual structure.

Primary targets:
- Recon topology,
- relationship/rival signatures,
- evidence truth language,
- contract objective/deadline visualization,
- market capability comparison,
- richer structured terminal output,
- History/postmortem timelines.

Constraints:
- recognition before reading, not visuals instead of precision,
- diagrams must represent real game structure,
- projected knowledge only.

Exit:
- a player can identify major relationship/evidence/operation states without reading every paragraph,
- visual and text representations agree.

## P3 — Onboarding + discoverability

Teach the fictional OS and capability model through use, not a detached wall-of-text tutorial.

Deliver:
- first-run orientation,
- contextual hints,
- command discovery/help,
- explainable icons/statuses,
- safe early affordances,
- optional reminders that do not become permanent noise.

Exit:
- a technically inexperienced player can form and execute a basic operation using in-game cues,
- expert players can dismiss/avoid repeated instruction.

## P4 — Accessibility + interaction comfort

Harden the game for long sessions and multiple interaction styles.

Deliver:
- keyboard navigation,
- focus management,
- contrast audit,
- non-color state cues,
- reduced motion,
- UI/text scale,
- reduced transparency where needed,
- readable dense-data treatment,
- screen-reader semantics where practical for React UI.

Exit:
- core web flow is operable without precision pointer use,
- distro choice cannot break accessibility guarantees.

## P5 — New-run, save, migration + recovery hardening

Close the browser lifecycle gaps before beta.

Deliver:
- explicit new-run flow,
- real run seed variation without exposing it as a power choice,
- representative historical-save fixtures,
- migration tests,
- refresh/crash recovery behavior,
- corrupt/incompatible save messaging,
- active-run/history edge-case hardening.

Exit:
- representative historical saves either migrate safely or fail readably,
- reload/crash cannot revive terminal runs or silently destroy active progress,
- repeated new runs are not all the fixed alpha seed.

## P6 — Beta balance + telemetry follow-ups

Use measured policies rather than tuning by impression.

Add coverage for the known Phase 8 gaps:
- purchasing/market affordability policy,
- pressure-band reachability,
- seed-varied new runs,
- novice/low-knowledge behavior where useful,
- run length/endings/economy/rank/failure distributions after UI/onboarding changes.

Exit:
- market affordability is measured before price changes,
- `known`/`entangled` pressure bands are either justified/reachable or deliberately redesigned,
- no rank gate is introduced.

## P7 — Ending/history polish + room/audio atmosphere

Polish the emotional ends of runs and the physical frame around the computer.

Deliver:
- ending presentation polish,
- run-history readability,
- causal postmortem presentation,
- room atmosphere,
- restrained UI/system audio,
- physical warning cues that do not reveal hidden truth.

Exit:
- endings feel intentionally authored rather than debug states,
- audio/room presentation supports tension without becoming required information.

## P8 — Browser performance + web release hardening

Finish the web game rather than starting desktop packaging early.

Deliver:
- performance profiling,
- large-list/graph stress checks,
- animation cost audit,
- browser compatibility,
- production build/static-export checks,
- recovery/error polish,
- release checklist.

Exit:
- web beta is feature-complete and stable,
- remaining planned work is Phase 10 host/distribution integration rather than gameplay/UI architecture.

## Cross-cutting rules

- Rank remains reputation, never power.
- Terminal and GUI use the same commands/capabilities.
- UI animation never owns simulation time.
- Presentation does not enter deterministic simulation output.
- Distros/themes are cosmetic.
- Visualizations may not expose hidden authoritative truth.
- Prefer local verification over GitHub Actions when hosted CI is unnecessary.
